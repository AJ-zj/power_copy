## 二、关键约束（复审发现 + 项目负责人确认）

### 约束 1：平台 Embedding 待确认

只读探测 `GET /v1/models` 返回 26 个模型，全部是对话模型，未见 embedding 端点。

**项目负责人确认（2026-11-26）**：当前模型列表未发现 Embedding，**不等于证明平台不存在该服务**。需进一步核实。

**应对**：优先评估本地 Embedding 模型，暂不使用第三方付费 Embedding API。候选 BGE-small-zh-v1.5、BGE-M3、Qwen3-Embedding-0.6B；先核实 CPU/GPU/内存/磁盘/依赖/许可证，未经确认不下载大型模型。

### 约束 2：语料规模小

当前 2 份政策、26 个切片。

**影响**：任何复杂索引方案的收益都无法体现。

**应对**：优先打磨基础检索质量，等语料规模化后再评估复杂方案。

### 约束 3：无历史 Trace

Trace 只在内存中，刷新即丢。

**影响**：无法记录评测过程，无法做对照实验。

**调整（项目负责人确认）**：Trace 持久化降为 **P1**，暂不阻塞 RAG 开发。

### 约束 4：中文检索方案已定

**项目负责人批准（2026-11-26）**：
- 采用 SQLite FTS5 trigram 作为初始词法检索基线
- **必须设计少于 3 个字符的查询回退机制**
- 暂不引入 jieba，后续由真实评测决定是否增加中文分词和行业词典

## 三、分阶段路线

### 阶段 05-A：BM25 检索基线

**目标**：建立可量化的检索基线，作为所有后续方案的评价参照。

**前置**：
- 检索评测集（人工标注 30 条 query → 相关切片）
- Trace 持久化（P1，可选，用于记录评测过程）

**工作项**：

| 编号 | 任务 | 产出 |
|---|---|---|
| A1 | 设计 FTS5 虚表结构与同步机制 | 索引 DDL |
| A2 | **短查询回退机制**（< 3 字符） | 回退策略 |
| A3 | 实现 `search_chunks(query, k)` | 检索函数 |
| A4 | 构建评测集（30 条） | 标注数据 |
| A5 | 计算 Recall@10 / MRR / nDCG | 基线指标 |
| A6 | 接入 `search_policy` 工具（可选） | 工具升级 |

**关于短查询回退**（项目负责人明确要求）：

FTS5 trigram tokenizer 最小匹配长度是 3 个字符。少于 3 字符的查询（如"电价"、"安徽"）无法用 trigram 索引，必须设计回退：

1. 优先：前缀匹配（trigram 支持 `LIKE 'xx%'` 走索引）
2. 次选：回退到 `instr()` 全表扫描（数据量小可接受）
3. 兜底：提示用户补充关键词

**验收标准**：
- Recall@10 ≥ 业务可接受阈值（需业务方确认，建议 ≥ 70%）
- 检索延迟 < 100ms（本地 SQLite）
- 零新增依赖
- **1-2 字符查询有明确回退行为，不报错**

**风险**：中文分词质量。不引入 jieba 的前提下，trigram 对中文按 3 字切分，短词召回可能不足。需在评测中重点观察。

### 阶段 05-B：向量检索【已完成，2026-11-26】

**状态**：✅ 已实施（ADR-007）

**实际结果**

| 指标 | Lexical | Dense |
|---|---|---|
| Recall@10 | 0.4231 | **0.8421** |
| MRR | 0.4231 | **0.7234** |
| 证据不足用例 | **4/4** | 0/4 |

**H1 成立**（semantic+cross_clause 0 → 0.8085）
**H2 成立**（exact_keyword+short_word 0.8182）
**H3 已在 05.5-A 验证**（结论见下节，注意分类型持平）

**关键发现：互补而非替代**

- 词法优势：exact_keyword 1.000 / short_word 1.000
- 向量优势：semantic 0.833 / cross_clause 0.779 / policy_relation 1.000

**遗留问题**：Dense 无法表达「无证据」，需独立的证据充分性判断机制。

#### 05-B 原始设计依据（保留备查）

**目标**：在 BM25 基础上加入语义检索，验证是否优于基线。

**前置条件（满足其一）**：
1. 核实平台新增 embedding 端点
2. 决定引入本地模型（已核实硬件与许可证）
3. BM25 基线 Recall@10 低于阈值

**本地模型候选**（项目负责人指定方向）：

| 模型 | 参数量 | 特点 |
|---|---|---|
| BGE-small-zh-v1.5 | ~24M | 轻量，CPU 可跑 |
| BGE-M3 | ~568M | 多语言、多粒度 |
| Qwen3-Embedding-0.6B | ~0.6B | 中文强 |

**核实清单（未经确认不下载）**：
- [ ] CPU / GPU 可用性
- [ ] 内存与磁盘需求
- [ ] 依赖体积（torch 等）
- [ ] 许可证是否允许商用
- [ ] 推理速度是否可接受

**小规模优先 NumPy**（项目负责人要求）：

当前 26 个切片，向量维度按 512 计，矩阵仅 26×512，NumPy 暴力计算余弦相似度耗时 < 1ms。**不强制部署向量数据库**。

触发引入向量数据库的条件：
- 切片数 > 10 万
- NumPy 暴力检索延迟 > 50ms

**工作项**：

| 编号 | 任务 |
|---|---|
| B1 | 核实本地模型硬件与许可证 |
| B2 | 批量生成切片向量 |
| B3 | NumPy 精确检索实现 |
| B4 | 混合检索打分融合（加权/RRF） |
| B5 | 与 05-A 基线对照评测 |

**验收标准**：
- Recall@10 相比基线提升 ≥ 10 个百分点，否则不保留

**注意**：若提升不明显，应明确记录"本语料规模下向量检索无收益"，不强行引入。

### 阶段 05.5-A：混合检索【已完成，2026-11-26】

**状态**：✅ 已实施（ADR-008）

**基线配置**：rank_constant=60, lex_k=10, dense_k=10, final_k=10, 等权

**结果**

| 指标 | Lexical | Dense | Hybrid |
|---|---|---|---|
| Recall@10 | 0.4231 | 0.8421 | **0.9190** |
| MRR | 0.4231 | 0.7234 | **0.7811** |
| CER | 0.4231 | 0.7692 | **0.8462** |
| 证据不足 | **4/4** | 0/4 | 0/4 |

**H3 在 5/5 主指标成立，但分类型指标全部持平。**

> ⚠ **RRF 不保证所有查询均优于单路检索。**
>
> 实测中 Hybrid 的收益来自「同时拿到两路各自的上限」，而不是让某一类查询变好：
>
> | 类型 | Lexical | Dense | Hybrid | 判断 |
> |---|---|---|---|---|
> | exact_keyword | 1.000 | 0.833 | 1.000 | 持平（取词法上限） |
> | short_word | 1.000 | 0.800 | 1.000 | 持平（取词法上限） |
> | semantic | 0.000 | 0.833 | 0.833 | 持平（取向量上限） |
> | cross_clause | 0.000 | 0.779 | 0.779 | 持平 |
> | policy_relation | 0.000 | 1.000 | 1.000 | 持平 |
>
> 因此正确表述是「混合检索在总体指标上优于任一单路，但不保证每个查询都更好」，
> 而不是「混合检索全面优于单路」。

**未实现**：Weighted RRF、DBSF、Linear Fusion、Reranker、GraphRAG、Adaptive Router

**遗留**：证据充分性判断、语料规模、统计显著性检验

**后续**：本阶段的混合检索已在 V2.1 MVP-01 接入 Agent Runtime（ADR-009），
交付路线见 `roadmap-v2.1.md`。

### 阶段 05-C：政策关系增强

**目标**：建模政策间的关系，支撑"这条政策被谁替代"类查询。

**前置**：
- P0-4 政策生命周期建模（`effective_from` / `effective_to`）

**关键判断**：**不引入图数据库**。

理由：售电业务的核心关系是"替代/修订/引用"，用 SQLite 关系表即可表达。

**数据结构**：

```sql
CREATE TABLE policy_relations (
    source_policy_id TEXT NOT NULL,
    relation_type    TEXT NOT NULL,   -- supersedes / amends / references
    target_policy_id TEXT NOT NULL,
    evidence         TEXT,            -- 关系依据（原文引用或链接）
    created_at       TEXT NOT NULL,
    PRIMARY KEY (source_policy_id, relation_type, target_policy_id)
);
```

**工作项**：

| 编号 | 任务 |
|---|---|
| C1 | 政策生命周期字段扩展（`effective_from` / `effective_to`） |
| C2 | 关系表设计与迁移 |
| C3 | 关系抽取（规则 + LLM 辅助 + 人工验证） |
| C4 | 检索时关系扩展召回 |
| C5 | 前端展示"政策沿革" |

**关系抽取方案**（项目负责人确认）：

采用**规则抽取 + LLM 辅助抽取 + 人工验证**三结合：

| 方式 | 适用场景 | 例 |
|---|---|---|
| 规则抽取 | 明确的废止/替代措辞 | "自本规则施行之日起，XX 同时废止" |
| LLM 辅助 | 隐式引用、上下文推断 | "按照《XX 办法》有关规定执行" |
| 人工验证 | 高风险关系、金额/时限相关 | 所有进入正式推理链路前 |

**强制约束**：候选关系必须绑定**原始政策版本和证据位置**（`source_policy_id` + `source_version` + `evidence_text` + `evidence_offset`）。

**未经验证的高风险关系不得进入正式政策推理链路**。

**关于技术选型依据**（项目负责人明确）：政策数量和查询跳数只能作为**重评参考**，不能作为唯一技术选型依据。真正的判断标准是关系表达力与查询性能是否被验证为瓶颈。

**验收标准**：
- 能回答"《XX 规则》被哪条政策替代"
- 关系抽取准确率 ≥ 90%（人工抽查）

### 阶段 05-E：增量索引

**目标**：政策变更时只更新受影响的部分，不重建全量索引。

**前置**：
- P2-5 文档变更事件表

**已有的基础**（这是好消息）：

| 增量索引所需 | 当前状态 |
|---|---|
| 内容哈希 / 版本指纹 | ✅ 已有 `content_sha256` |
| 来源溯源（可回指文档） | ✅ 切片已带 `document_id` / `fetch_id` |
| 变更事件 | ❌ 缺失 |

FalkorDB 的工程文章指出，增量索引需要两个基础设施：内容哈希和来源溯源。**PowerCopy 已具备两者**，只缺"变更事件"这一项。

**工作项**：

| 编号 | 任务 |
|---|---|
| E1 | `policy_change_events` 表设计 |
| E2 | 版本写入时记录变更事件 |
| E3 | 索引消费者订阅事件 |
| E4 | 删除/下线场景的索引失效 |

## 八、评测集设计（项目负责人已批准）

首批 **30 条**测试问题，覆盖 6 类：

| 类型 | 数量 | 示例 |
|---|---|---|
| 精确关键词 | 6 | "电力市场运行基本规则" |
| 短词（< 3 字符） | 5 | "电价"、"安徽"、"结算" |
| 语义检索 | 6 | "电价怎么定" → 电价形成机制条款 |
| 跨条款 | 5 | 需要拼接多个条款才能回答 |
| 政策关系 | 4 | "哪条政策废止了 2005 年运营规则" |
| 证据不足 | 4 | 库中没有的政策，应返回 empty |

**标注要求**：

- 每条 query 标注相关切片
- **保留原文证据位置**（`policy_id` + `version` + `start` + `end` + 原文片段）
- 不仅依赖 Chunk ID（因为重新切片会导致 ID 变化）
- 正式评测前**冻结测试集版本**

**生成与审核流程**：

```text
Codex 辅助生成候选问题
    ↓
项目负责人核实（是否符合业务场景）
    ↓
业务人员审核（涉及专业政策解释时）
    ↓
冻结版本，写入 evaluations/
```
