## 一、路线调整说明

原 `roadmap-stage05.md` 把 GraphRAG、Adaptive Router、增量索引等技术升级作为
「阶段05 后续」，并隐含地把它们当作首篇文案产出的前置条件。

**这个假设需要修正。**

理由：

1. 混合检索已达到可用基线（Hybrid Recall@10 = 0.9190），足以支撑首篇文案的
   证据召回需求
2. GraphRAG 解决的是「政策关系推理」，而首篇文案主要是「引用条款 + 合规表述」，
   对关系推理的依赖不是硬性的
3. 继续无条件扩展底层技术模块，会把交付无限推迟

**新原则**：技术升级保留在路线图中，但**不再是首篇文案产出的前置条件**。
是否启动某个技术升级，由业务侧的真实需求驱动。

## 二、MVP 交付路线

### MVP-01 检索集成 ✅ 已完成（2026-11-26）

**目标**：让现有 Agent 真正能够安全、稳定地使用已实现的混合检索。

**交付**

| 项 | 内容 |
|---|---|
| 索引一致性 | 四状态严格区分：ok / single_path_unconfigured / fingerprint_missing / version_conflict |
| 版本冲突 | 即使 `allow_degrade=True` 也拒绝融合 |
| 模型一致性 | 索引绑定 commit + tokenizer 指纹，加载与每次检索都校验 |
| NPZ 安全 | `chunk_ids` 改定长 Unicode，`allow_pickle=False`；旧格式拒绝并指引重建 |
| 离线运行 | `local_files_only=True` 默认，缺模型报错不联网 |
| 新工具 | `search_policy_evidence` |
| 运行时 | `use_retrieval` 开关，默认关闭保持原行为 |
| 测试 | +55 项，全量 1189 passed |

**已知边界**

- 不判断证据充分性（候选 = 可能的证据，不是已核实的证据）
- 不保证 RRF 在所有查询上优于单路
- 语料仍为 26 切片 / 2 份政策

### MVP-02 政策研究与证据包

**目标**：把「检索候选」加工成可交付的**证据包**。

**范围**

1. 多轮检索与证据筛选：对同一研究问题做多次不同角度的检索
2. 证据去重与归并：同一政策的多段证据合并为条款级证据项
3. 证据充分性判断：区分「找到相关条款」与「条款足以回答」两个层级
4. 证据包结构：政策清单 + 每条证据的原文 + 偏移 + 适用性说明
5. 缺口标注：明确列出「库中无对应政策」的部分

**不做**

- 不做政策关系推理（留待技术升级）
- 不做自动撰写

**验收关键**

- 证据包中每条证据都能追溯到原文与偏移
- 「证据不足」必须显式表达，不能靠相似度阈值猜测

---

### MVP-03 文案生成

**目标**：基于证据包生成合规文案。

**范围**

1. Skill 定义：业务话术模板、必须包含的要素、禁止表述
2. 证据引用：每个事实性句子必须绑定证据 ID
3. 生成约束：无证据不得陈述事实、不确定必须标注
4. 输出结构：正文 + 引用清单 + 待核实项

**不做**

- 不做自动审核
- 不做多轮改写

**验收关键**

- 生成的每个事实性陈述都能映射到证据包中的条目
- 无证据支撑的断言必须被拒绝或标为待核实

---

### MVP-04 审核及修订

**目标**：对生成文案做结构化审核并支持修订。

**范围**

1. 审核规则：事实准确性、合规表述、时效性、完整性
2. 审核结论结构：通过 / 需修订 / 拒绝，附具体问题条目
3. 修订流程：按审核意见定位到具体句子并重写
4. 修订历史：保留每轮修订的差异

**验收关键**

- 审核结论必须可定位到具体句子
- 修订后需重新走引用校验

---

### MVP-05 Content Studio 与人工审批

**目标**：人机协作的内容生产界面。

**范围**

1. 工作台新增 Content Studio 页面
2. 证据包审阅界面：原文、偏移、来源链接
3. 草稿编辑与批注
4. 人工审批：通过 / 驳回 / 要求补充证据
5. 审批记录留存

**验收关键**

- 审批人能看到每条事实的原始证据
- 审批动作有审计记录

---

### MVP-06 企业业务验收

**目标**：业务侧真实验收。

**范围**

1. 业务人员抽样评审文案质量
2. 政策解释的准确性由业务专家确认
3. 建立业务验收评测集（区别于开发评测集）
4. 收集真实问题与失败案例

**验收关键**

- 业务侧认可文案可直接使用或小改后使用
- 开发评测集与业务验收结论一致性有量化记录

## 三、技术升级路线（保留，非前置）

以下能力保留在路线图中，但**不阻塞 MVP 交付**。是否启动由业务需求驱动。

### 05-C 政策关系增强

**解决的问题**：政策之间的「替代 / 修订 / 引用」关系推理。

**当前状态**：未建设。现有 `policy_relation` 类查询只能检索**承载关系表述的原文片段**，
不能做图关系推理。这是两件不同的事。

**触发条件**：
- 业务侧明确需要回答「某政策是否仍有效 / 被哪份文件替代」
- 或 MVP-02 证据包频繁出现「需要跨政策关系才能回答」的缺口

### 05-D 自适应路由 / Agentic RAG

**解决的问题**：根据问题类型选择检索策略，而非固定 RRF。

**触发条件**：
- 有足够数据证明某些查询类型单路优于混合
- MVP-02 的证据筛选阶段积累了大量查询-策略匹配数据

### 05-E 增量索引

**解决的问题**：语料扩大后全量重建成本过高。

**触发条件**：
- 政策数量超过 500 份
- 全量重建时间超过可接受范围

### 证据充分性判断（Reranker / 阈值 / 分类器）

**当前状态**：**最重要的技术空缺**。向量检索必然返回 Top-K，
相似度高低不等于有证据。

**触发条件**：
- MVP-02 需要区分「有证据」与「无证据」
- 这件事很可能在 MVP-02 中就必须解决

### ONNX 加速

**当前状态**：用 torch CPU，未装 ONNX。冷启动 31 秒。

**触发条件**：
- 冷启动影响生产体验
- 或需要降低部署体积

## 五、交付原则

1. **每个 MVP 都必须能独立验收**，不依赖后续 MVP
2. **不做未经业务需求驱动的底层扩展**
3. **证据可追溯是硬要求**，任何 MVP 都不得牺牲
4. **不虚构进度**：技术空缺如实记录，不用「基本可用」掩盖
